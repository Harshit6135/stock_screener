# Implemented in v3, not yet implemented in v4

Compared `dead-code-cleanup` at `dabff599` (the `stocks_screener_v2_dead_code_cleanup` worktree) with `feature/codex_enhancement` at `eac80fe3` (this workspace). This review used Python, HTML, JavaScript, configuration, and route code; Markdown files were excluded. A different endpoint name or storage design alone was not counted as a gap. Paths below are relative to the named worktree, and line numbers point to the implementation or the closest v4 counterpart.

1. **Automatic day-zero stock universe with YFinance enrichment and screening.** V3 joins NSE and BSE CSV records by ISIN, excludes mutual funds and ETF-like entries, tries NSE/BSE YFinance ticker variants, stores company/sector/industry/market-cap metadata, applies the ₹500-crore market-cap and ₹75 price thresholds, and then syncs the filtered universe with Kite. V4 syncs Kite/NSE and BSE instruments and accepts separately published reference snapshots, but has no equivalent automatic YFinance enrichment, master-universe build, or threshold screen. Evidence: v3 `src/services/init_service.py:26,90,200,216,295,327,440`; v3 `src/config/app_config.py:4-5`; v4 `src/application/market_jobs.py:67,149`; v4 `src/application/reference_web.py:148,186`.

2. **YFinance fallback for the NIFTY 500 research benchmark.** V3's benchmark adaptor caches a date-range close series and falls back from Kite to YFinance when Kite fails or has no rows; Strategy 2 indicator calculation calls it. V4's Strategy 2 daily job requires a persisted, same-day NIFTY 500 history and errors if it is absent or stale. Evidence: v3 `src/adaptors/benchmark_adaptor.py:42,64,179`; v3 `src/services/indicators_service.py:318,494`; v4 `src/application/research_jobs.py:273-283`; v4 `src/application/research_strategy2.py:38-46`.

3. **Persisted, patchable historical indicator catalogue.** V3 defines a broad named indicator registry (including EMA, ROC, stochastic, PPO, MACD, Bollinger, ATR, and derived fields), persists per-symbol/date indicator rows, can selectively recompute named columns across existing history, and exposes a named-value query. V4 computes the subset needed for its daily strategy feature snapshots and can recalculate a strategy/date for selected symbols, but does not persist or expose the full named indicator time series or provide a column-selective historical backfill. Evidence: v3 `src/config/indicators_config.py:228-345`; v3 `src/services/indicators_service.py:296,437`; v3 `src/api/v1/routes/indicators_routes.py:95,125`; v4 `src/application/research_strategy1.py:65,157`; v4 `src/application/research_strategy2.py:38,158`; v4 `src/application/research_web.py:64,203`.

4. **Direct bulk market-data and indicator maintenance API.** V3 exposes bulk OHLCV and indicator insert endpoints, per-symbol market-data and indicator deletion, and all-symbol/per-symbol historical queries and latest-date lookups. V4 has bar read APIs, provider fetch/import jobs, and research snapshots, but no equivalent HTTP maintenance surface for directly inserting or deleting arbitrary raw market/indicator rows. Evidence: v3 `src/api/v1/routes/marketdata_routes.py:21,34,44,53,62,78,111`; v3 `src/api/v1/routes/indicators_routes.py:17,30,40,49,58,74`; v4 `src/application/market_web.py:201`; v4 `src/application/research_web.py:203`; v4 `src/application/composition.py:119-130`.

5. **Selective, in-order pipeline execution from one request.** V3's `/api/v1/app/run-pipeline` accepts separate switches for initialization, market data, indicators, percentiles, scores, and rankings, runs enabled steps in dependency order, and skips downstream steps after a failure. V4's durable pipeline orchestrates reference/market refresh as one boolean and schedules daily research stages; individual job kinds exist, but the v3 per-stage selection contract is absent. Evidence: v3 `src/api/v1/routes/app_routes.py:110-260`; v4 `src/application/pipeline_jobs.py:45-159`; v4 `src/application/composition.py:119-135`.

6. **Date-cutoff cleanup and dependent rebuild.** V3 can delete data after a supplied date from individually selected market-data, indicator, percentile, score, and ranking tables, then rebuild percentile → score → ranking from a cutoff. V4 supports immutable snapshots, pipeline runs, and a selected-symbol/day research recalculation, but has no matching cutoff cleanup or stage-selective downstream rebuild API. Evidence: v3 `src/api/v1/routes/app_routes.py:70-108,262-341`; v4 `src/application/research_web.py:64-88`; v4 `src/application/pipeline_jobs.py:45-88`.

7. **Continuously updated Kite holdings-price ticker.** V3 resolves current holdings to Kite instrument tokens, seeds previous closes, starts a WebSocket ticker, caches last prices and percentage change, and offers start/prices/stop endpoints. V4 has a Kite streaming adaptor for intraday stop alerts, but its portfolio ticker reads the latest stored daily bar and its SSE route sends one snapshot; there is no connected live holdings-price cache/readout equivalent. Evidence: v3 `src/api/v1/routes/investment_routes.py:205-307`; v3 `src/adaptors/kite_adaptor.py:247-403`; v4 `src/application/providers.py:100-187`; v4 `src/application/portfolio_web.py:278-339`.

8. **Integrated legacy dashboard workflow.** V3 serves `templates/dashboard.html` at `/`; its JavaScript drives the multi-tab pipeline, portfolio, action approval/editing, backtest history, configuration, and live-price controls. V4 still contains those assets but does not render the template or register the `/api/v1` endpoints they call. Its `/app`, `/pipeline`, `/actions`, `/backtest`, and `/portfolio` pages provide smaller v2 workflows, leaving the combined v3 browser experience unimplemented. Evidence: v3 `run.py:63-67`; v3 `templates/dashboard.html:204,287`; v3 `static/js/dashboard.js:242,266,616,1019,1337`; v4 `run.py:65-79`; v4 `src/application/dashboard_web.py:10-205`.

9. **Live orchestration log stream.** V3 provides a continuous server-sent stream of pipeline log lines, including keepalive pings, and the dashboard opens it before submitting a pipeline run. V4 exposes persisted job events as a JSON query, but no continuous orchestration log stream. Evidence: v3 `src/api/v1/routes/app_routes.py:42-67`; v3 `static/js/dashboard.js:240-266`; v4 `src/application/web.py:85-97`.

10. **Generated OpenAPI specification and interactive API browsers.** V3 registers its routes with `flask-smorest` and configures OpenAPI 3, Swagger UI, and ReDoc. V4 registers plain Flask blueprints and has no equivalent generated specification or interactive API documentation route. Evidence: v3 `run.py:2-3,35,43-59`; v3 `src/config/flask_config.py:4-11`; v4 `run.py:65-84`.

11. **Delete a saved backtest run from the application.** V3 exposes `DELETE /api/v1/backtest/history/<run_id>` and removes the saved run and its files. V4 lists and reads current and imported legacy runs, but has no run-deletion operation. Evidence: v3 `src/api/v1/routes/backtest_routes.py:102-128`; v3 `src/repositories/backtest_history_repository.py:128`; v4 `src/application/backtest_web.py:13-102`.

12. **Convenience ranking lookup with date normalization and close price.** V3 lets callers request one symbol's ranking for an arbitrary date, normalizes that date to the most recent Friday on or before it, and returns the associated close price (or a zero-rank fallback). V4 can query ranking snapshots by symbol and exact week, but does not provide the Friday normalization or price-enriched single-symbol response. Evidence: v3 `src/api/v1/routes/ranking_routes.py:42-105`; v3 `src/utils/date_utils.py:66`; v4 `src/application/research_web.py:48-62,203-238`.

These are source-level gaps, not a claim that every v3 endpoint is desirable in v4. In particular, v4's snapshot, job, and account models intentionally differ from v3's mutable tables; the list describes missing behavior or interfaces, not a proposed implementation order.
